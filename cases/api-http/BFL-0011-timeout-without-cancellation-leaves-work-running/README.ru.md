# Timeout Without Cancellation Leaves Work Running

API-запрос получает timeout, но backend продолжает работу и помечает export как завершенный.

Этот case показывает, что timeout ответа и отмена работы — это разные вещи.

## Metadata

- ID: `BFL-0011`
- Category: `api-http`
- Secondary categories: `reliability-failure-recovery`, `performance-scaling`
- Level: `middle-advanced`
- Technologies: `python`, `fastapi`, `pytest`
- Failure modes: `timeout`, `partial-failure`
- Patterns: `graceful-shutdown`
- Status: `draft`

## Проблема

Endpoint запускает долгую операцию export. Когда запрос получает timeout, сломанная реализация всё равно завершает export во внутреннем состоянии.

Клиент получает `504 Gateway Timeout`, но сохраненный export имеет статус `completed`.

## Почему это происходит в production

Timeout часто добавляют вокруг ответа клиенту, а сама работа продолжает выполняться в фоне или в задаче, которую никто не отменил.

Из-за этого состояние становится неоднозначным: клиент повторяет запрос, потому что увидел timeout, но backend уже мог изменить данные, вызвать другой сервис или создать файл.

## Сценарий бага

1. Export `100` находится в состоянии `pending`.
2. Клиент запускает export.
3. Запрос получает timeout.
4. API возвращает `504`.
5. Backend всё равно помечает export как `completed`.
6. Клиент не понимает, операция упала или завершилась.

## Сломанная реализация

Сломанный код воспринимает timeout как ошибку ответа, но не как сигнал отмены:

```python
if simulate_timeout:
    export.status = "completed"
    export.result = "report.csv"
    raise ExportTimeoutError()
```

## Где происходит ошибка

Ошибка находится в `broken/repository.py`, внутри `run_export`. Ветка timeout всё равно записывает финальное успешное состояние.

Из-за этого контракт API становится ложным: ответ говорит, что операция не успела завершиться, а backend-состояние говорит, что она завершена.

## Как поймать этот баг

Проверяй состояние после timeout. Тест, который смотрит только на `504`, слишком слабый.

Полезный тест отправляет запрос с timeout, потом читает export и проверяет, что он не был завершен.

## Падающий тест

`tests/test_broken.py` ожидает, что export после timeout станет `cancelled` и не будет иметь результата.

Сломанная реализация сохраняет `completed` и `report.csv`, поэтому тест падает.

## Диагностика

Система ломается потому, что обработку timeout путают с отменой работы.

Вернуть timeout клиенту не значит автоматически остановить backend. Код должен явно решить, что происходит с состоянием операции, если запрос уже не может безопасно завершиться.

## Исправленная реализация

Исправленная реализация помечает операцию как отмененную, когда сработала ветка timeout:

```python
if simulate_timeout:
    export.status = "cancelled"
    export.result = None
    raise ExportTimeoutError()
```

Для реальной долгой работы часто лучше использовать модель job/status: запустить job, вернуть ID, а клиент пусть проверяет статус. Так timeout становится понятным, а не прячется внутри одного длинного запроса.

## Файлы

- `broken/` — намеренно небезопасная реализация
- `fixed/` — исправленная реализация
- `tests/` — тесты, которые показывают баг и проверяют исправление

## Production notes

- Не считай, что timeout клиента автоматически отменяет backend-работу.
- Храни состояние долгих операций явно.
- Для долгих задач чаще подходит API с job ID и отдельной проверкой статуса.
- Делай повторы безопасными, когда клиент не может понять, завершилась ли операция после timeout.

## Trade-offs

Отмена работы при timeout сохраняет состояние честным, но может выбросить полезный частичный прогресс.

Продолжать работу тоже иногда нормально, но тогда API должен возвращать стабильный job ID и статус, а не неоднозначный timeout из длинного синхронного запроса.
