# Background Job Commits Too Early Before External Call

## Summary

FastAPI фоновая задача помечает заказ как подтвержденный до того, как успешно прошла внешняя отправка уведомления, поэтому упавшее уведомление оставляет заказ в ghost state.

API возвращает 202 сразу, поэтому вызывающий видит успех, а база тихо с этим не согласна. Этот case показывает частичный сбой: durable commit в паре с более поздним side effect, который все еще может упасть.

## Проблема

API подтверждает заказ, а затем отправляет внешнее уведомление. В сломанной реализации код сохраняет `order.status = "confirmed"` до того, как внешний вызов завершился успешно.

Если внешний вызов падает, пользователь получает ошибку, но база уже говорит, что заказ подтвержден.

## Почему это происходит в production

Такое появляется, когда код считает многошаговый процесс единым успешным действием. Запись в базе уже сохранена, но последующий HTTP-вызов, email, payment request или webhook всё ещё может упасть.

Главная опасность в том, что повторная обработка начинает работу из неверного состояния. Система может пропустить нужное действие, потому что считает заказ уже подтвержденным.

## Сценарий бага

1. Заказ `100` находится в состоянии `pending`.
2. Приходит `POST /orders/100/confirm` — endpoint возвращает `202` сразу и ставит фоновую задачу.
3. Фоновая задача сохраняет `status = confirmed`.
4. Сервис уведомлений падает.
5. Фоновая задача молча проглатывает ошибку (fire-and-forget).
6. Заказ остается подтвержденным в базе, хотя уведомление так и не было отправлено.

## Сломанная реализация

Сломанный код слишком рано сохраняет финальное состояние:

```python
order.status = "confirmed"
session.commit()
send_confirmation_notification()
```

## Где происходит ошибка

Ошибка находится в `broken/repository.py`, внутри `confirm_order`. Функция пересекает границу между состоянием в базе и внешним действием, но делает commit до того, как внешнее действие стало безопасным.

В итоге база перестает честно отражать то, что реально произошло.

## Как поймать этот баг

Проверяй не только успешный путь, но и путь с падением. Нужно специально заставить внешний сервис упасть, а потом прочитать заказ из базы.

Важен не только HTTP status. Важна проверка, что неуспешное внешнее действие не оставило после себя финальное успешное состояние.

## Падающий тест

`tests/test_broken.py` ожидает, что заказ останется `pending`, если внешнее уведомление упало.

Endpoint правильно возвращает `202`, но фоновая задача уже сохранила `status = confirmed` до того, как уведомление упало — поэтому в базе `confirmed` вместо `pending`, и тест падает.

## Диагностика

Проверки, валидация и запись в базу могут быть правильными по отдельности, но весь процесс всё равно может быть небезопасным.

Backend должен явно понимать границу между локальным состоянием и внешними действиями. В более крупной системе это часто решают через outbox table: сначала надежно записывают событие, а потом отдельный повторяемый worker доставляет его наружу.

## Исправленная реализация

Исправленная реализация не сохраняет финальный успех до успешного уведомления:

```python
send_confirmation_notification()
order.status = "confirmed"
order.confirmation_sent = True
session.commit()
```

Для маленького lab case этого достаточно, чтобы состояние было честным. В production обычно надежнее использовать outbox pattern, потому что внешний вызов нельзя сделать частью той же транзакции базы.

## Production notes

- Не помечай работу завершенной до того, как все нужные условия действительно выполнены.
- Считай внешние вызовы ненадежными, даже если обычно они работают.
- Используй понятные состояния вроде `pending`, `processing`, `confirmed`.
- Для надежных внешних действий стоит рассмотреть outbox pattern.

## Trade-offs

Вызвать внешний сервис до сохранения финального состояния просто, но это всё равно не делает внешний сервис атомарным вместе с базой.

Outbox надежнее для production-процессов, но добавляет таблицу, доставщик событий, повторы и мониторинг. Для маленького кода иногда достаточно явных переходов состояния.
