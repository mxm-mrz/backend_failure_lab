# Missing Database Constraint Allows Duplicate Emails

Backend проверяет, существует ли email перед созданием пользователя, но база не запрещает дубликаты.

Этот case показывает, что проверки на уровне приложения недостаточно для важных правил данных.

## Metadata

- ID: `BFL-0010`
- Category: `database-transactions`
- Secondary categories: `security-auth`, `reliability-failure-recovery`
- Level: `junior`
- Technologies: `python`, `fastapi`, `postgresql`, `sqlalchemy`, `pytest`
- Failure modes: `race-condition`
- Patterns: `transaction-boundary`
- Status: `draft`

## Проблема

Код проверяет, есть ли пользователь с таким же email, и если нет — создает нового пользователя.

При обычных последовательных запросах это работает. Но это не защищает данные надежно. Два одновременных запроса могут оба пройти проверку до commit, а потом оба вставить одинаковый email.

## Почему это происходит в production

Такой баг появляется, когда уникальность считают только бизнес-логикой в коде. Метод сервиса выглядит нормально, ручная проверка тоже обычно проходит.

Но при одновременных запросах проверка и вставка — это две разные операции. Если в базе нет ограничения, база не обязана отклонять вторую вставку.

## Сценарий бага

1. Request A проверяет `john@example.com` и не находит пользователя.
2. Request B проверяет `john@example.com` и тоже не находит пользователя.
3. Request A вставляет пользователя и делает commit.
4. Request B вставляет пользователя и делает commit.
5. В базе теперь два пользователя с одинаковым email.

## Сломанная реализация

В сломанной модели `email` описан как обычная колонка:

```python
email = mapped_column(String, nullable=False)
```

Код полагается на проверку перед вставкой, а не на ограничение базы.

## Где происходит ошибка

Ошибка находится в `broken/models.py`. У колонки `users.email` нет `unique=True`, поэтому база не защищает правило уникальности.

Проверка в `broken/repository.py` полезна для понятной ошибки пользователю, но она не может быть единственной защитой.

## Как поймать этот баг

Нужно смоделировать две сессии, которые обе проходят проверку до того, как первая вставка завершилась commit.

Хороший тест должен доказывать, что сама база отклоняет дубликат. Если тест просто два раза подряд вызывает endpoint, он может пропустить гонку, потому что второй запрос уже видит первого созданного пользователя.

## Падающий тест

`tests/test_broken.py` ожидает, что вторая вставка вызовет `IntegrityError`.

В сломанной реализации нет уникального ограничения, поэтому вторая вставка проходит успешно и тест падает.

## Диагностика

Система ломается потому, что важное правило живет только в коде приложения.

Если правило всегда должно быть верным для сохраненных данных, его нужно защищать на границе базы. Проверки в приложении помогают сделать ошибку удобнее, но ограничения базы защищают данные при одновременных запросах.

## Исправленная реализация

Исправленная модель добавляет уникальность для email:

```python
email = mapped_column(String, nullable=False, unique=True)
```

Проверка перед вставкой остается, чтобы вернуть понятный `409 Conflict`. Но финальное решение теперь принимает база. Если два запроса пересеклись, один insert пройдет, а второй безопасно упадет.

## Как запустить

Из корня репозитория:

### Сломанная версия

```bash
make broken CASE=BFL-0010
```

Ожидаемо: тест должен упасть, потому что одинаковые email можно вставить, если оба запроса прошли проверку заранее.

### Исправленная версия

```bash
make fixed CASE=BFL-0010
```

Ожидаемо: тесты должны пройти, потому что база отклоняет дубликат email.

## Файлы

- `broken/` — намеренно небезопасная реализация
- `fixed/` — исправленная реализация
- `tests/` — тесты, которые показывают баг и проверяют исправление

## Production notes

- Используй ограничения базы для правил вроде уникального email, username или внешнего ID.
- Оставляй проверки в приложении для более понятных API-ответов, но не полагайся только на них.
- Обрабатывай ошибки целостности базы и возвращай стабильную ошибку, например `409 Conflict`.
- Добавляй тесты, которые моделируют пересечение сессий, а не только последовательные запросы.

## Trade-offs

Предварительная проверка дает понятные ошибки и в обычных случаях не делает лишнюю попытку вставки.

Но уникальное ограничение всё равно нужно, потому что оно защищает систему при одновременных запросах. Минус в том, что код должен аккуратно обрабатывать ошибки базы, а не считать предварительную проверку достаточной.
